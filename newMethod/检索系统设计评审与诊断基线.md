# 材料数据集检索系统设计评审与诊断基线

> 用途：长期记录当前检索系统的主要问题、改进方向、教师问题的设计方案，以及分阶段诊断基线的定义与实施方法。
>
> 当前实验结果：Canonical Macro-F1 为 56.00%，Family Macro-F1 为 63.54%。这说明系统已经能够找到一部分方向正确的数据集家族，但在精确实体识别、候选召回、证据控制和最终集合选择方面仍有明显改进空间。

---

## 1. 对当前实验结果的判断

### 1.1 Family 明显高于 Canonical 和 Strict

当前结果为：

| 匹配方式 | Macro Precision | Macro Recall | Macro F1 |
|---|---:|---:|---:|
| Strict | 43.59% | 32.88% | 35.94% |
| Canonical | 63.46% | 53.40% | 56.00% |
| Family | 69.87% | 63.40% | 63.54% |

Family 指标明显高于 Canonical 和 Strict，说明一部分错误不是完全不相关，而是：

- 推荐到了同一数据集家族的另一个版本；
- 推荐到了公共源，而论文实际使用的是公共源的派生数据集；
- 推荐到了 JARVIS、Materials Project 或 OQMD 家族，但没有命中指定子集；
- 数据集名称、别名、缩写或版本没有准确对齐。

因此，最终错误应至少拆成三类：

1. 正确数据集及其家族完全没有被召回；
2. 召回了正确家族，但没有识别到精确数据集实体；
3. 正确候选已经存在，但在重排或最终集合选择中被删除。

### 1.2 Recall 是当前更突出的瓶颈

Canonical Macro Precision 为 63.46%，Recall 为 53.40%；Family Macro Precision 为 69.87%，Recall 为 63.40%。系统并不是完全无关地推荐，而是漏掉了较多论文实际使用的数据集。

因此当前的优化顺序应是：

1. 保证 gold 数据集能够进入候选池；
2. 提高正确候选的排序；
3. 最后压缩结果数量和选择最小数据集集合。

如果候选池本身没有 gold 数据集，调整最终重排权重和返回数量无法解决问题。

### 1.3 Recall@3 到 Recall@5 增长很小

Canonical Recall@3 为 51.47%，Recall@5 为 53.40%；Family Recall@3 为 61.47%，Recall@5 为 63.40%。

增加第 4、5 个结果带来的收益非常有限，可能说明：

- gold 数据集没有进入最终候选；
- gold 数据集排名远低于第 5 名；
- 第 4、5 名主要是图扩展产生的低质量候选；
- 最终集合选择偏向重复的公共数据集或历史用途丰富的数据集。

因此，不应优先继续增加最终返回数量，而应进行完整的链路诊断。

### 1.4 当前评价测量的是“论文选择复现能力”

论文实际使用的数据集不一定是某个任务唯一合理的数据集。因此，当前 Strict、Canonical 和 Family 指标主要回答：

> 系统能否复现论文作者实际使用的数据集？

它并不能完整回答：

> 系统推荐的数据集是否也适合这个任务？

后续应将评价拆成：

1. **选择复现性**：是否命中论文实际使用的数据集；
2. **任务可用性**：推荐数据集是否满足材料、性质、阶段和约束；
3. **专家相关性**：未命中论文数据集时，推荐是否仍然合理；
4. **证据正确性**：推荐理由是否由相关 DatasetUse 和论文证据支持。

### 1.5 13 组测试数据只适合作为诊断集

13 组数据可以用于发现系统错误和做初步消融，但不足以证明某个排序策略具有普遍优势。单个样本的变化可能明显影响 Macro 指标。

建议后续：

- 保留 13 组作为固定开发集；
- 扩充一个不参与调参的测试集；
- 报告 bootstrap 置信区间；
- 同时进行逐案例错误分析。

## 2. 当前设计的主要问题及优先级

## P0：候选评分使用了过多“全部历史 DatasetUse”

当前候选生成后，会读取该数据集的全部历史 DatasetUse。任务、性质、阶段、角色和最终覆盖判断都可能受全部历史用途影响。

这会产生公共数据集流行度偏置：

```text
Materials Project 历史用途很多
→ 覆盖过很多任务、性质和阶段
→ 对大量查询都容易获得较高分数
```

而一个用途高度匹配、但只出现过一次的 task-specific 数据集可能得分更低。

### 建议

将证据分为三层：

- `E_path`：本轮召回和图路径直接发现的 DatasetUse；
- `E_relevant`：该数据集全部历史用途中，与本次查询最相关的 Top-3 或 Top-5；
- `E_global`：全部历史用途，只作为弱背景。

可以采用：

\[
S(d,q)=0.5S(E_{path})+0.4S(E_{relevant})+0.1S(E_{global})
\]

其中，阶段、角色和性质覆盖应主要由 `E_path` 和 `E_relevant` 决定，不能由任意历史用途无限补齐。

## P0：缺少材料、性质、阶段的层次化语义体系

QueryPlan 中虽然有材料、性质、阶段、角色和约束字段，但这些字段目前仍主要作为字符串处理。简单分词重叠难以表达：

- formation energy 与 thermodynamic stability 的关系；
- oxide 与 inorganic crystal 的上下位关系；
- structure prediction 与 candidate generation 的流程关系；
- training、validation 和 label source 的角色差异。

### 建议

建立三套受控体系：

1. 材料类别本体及上下位关系；
2. 性质别名、上下位和代理性质关系；
3. 研发宏观阶段、子阶段和输入输出关系。

## P0：没有独立评估每一层的 gold 保留情况

最终 F1 下降可能来自：

- Dense/BM25 没有召回；
- RRF 截断；
- 图扩展没有映射到 Dataset；
- 候选聚合或公共源映射错误；
- 确定性重排排名过低；
- LLM 重排或集合选择删除了正确候选。

只看最终结果无法定位是哪一层的问题。必须建立第 7 节中的诊断基线。

## P1：图扩展缺少严格的路径语义约束

同一篇论文中的 DatasetUse 可以通过 Paper 横向传播：

```text
DatasetUse A → Paper → DatasetUse B
```

这只说明它们出现在同一篇论文中，并不说明它们对应同一任务、阶段、性质或使用角色。

### 建议

对不同路径赋予不同可靠度：

| 路径 | 语义 | 建议权重 |
|---|---|---:|
| Task→Stage→DatasetUse→Dataset | 直接任务用途 | 1.00 |
| Stage→DatasetUse→Dataset | 直接阶段用途 | 0.95 |
| DatasetUse→Dataset | 直接使用关系 | 1.00 |
| Dataset→DatasetUse→Task | 历史反向用途 | 0.65 |
| Task→Paper→DatasetUse | 论文级间接关系 | 0.35 |
| DatasetUse→Paper→DatasetUse | 同论文共现 | 0.20 |

对弱路径增加材料、性质和任务一致性检查。发生明显冲突时停止扩展或大幅降权。

## P1：QueryPlan 没有充分控制第一阶段检索

当前查询主要由原始问题、材料、性质、任务子句和阶段子句拼接。constraints 和 usage role 没有有效控制初始召回。

### 建议

分通道构造查询：

- `Q_material`：材料范围；
- `Q_property`：目标性质；
- `Q_task`：任务目标；
- `Q_stage`：所需阶段；
- `Q_role`：训练、验证、筛选、标签来源等角色；
- `Q_constraint`：公开性、实验/计算来源、数据规模、输入限制；
- `Q_joint`：材料、性质和任务联合查询。

不同通道不应全部等权，而应根据查询中各字段的特异性动态调整。

## P1：LLM rerank 接收到的 DatasetUse 证据质量不稳定

大型公共数据集可能有很多历史用途，但 LLM 只看到原始顺序中的前若干条，而不一定看到与本次问题最相关的用途。分批重排也缺少跨批校准。

### 建议

1. 先按当前查询对 DatasetUse 排序；
2. 只提供最相关的 Top-5；
3. 每批放入固定锚点候选；
4. 让 LLM 分别输出材料、任务、性质、阶段、约束和证据质量分数；
5. 不让单一 relevance 分数承担全部判断。

## P2：最终选择后没有约束合规复核

如果用户明确要求公开数据或实验数据，违反要求的候选仍可能因任务相关性较高进入结果。

### 建议

在集合选择前增加 `Constraint Compliance Gate`：

- 硬约束：违反时删除；
- 软约束：违反时扣分；
- 信息未知：保留但明确标注不确定。

## P2：gold 实体和 Wiki 覆盖范围需要审查

如果 gold 数据集没有进入 Wiki，检索系统原则上不可能将其召回。应给每个 gold 增加：

```json
{
  "name": "Experimental formation energy dataset",
  "canonical_id": "experimental_formation_energy",
  "family_id": "experimental_formation_energy",
  "exists_in_wiki": true,
  "recommendable": true,
  "source_dataset_id": null
}
```

分别报告：

- 对全部 gold 的 Recall；
- 对 `exists_in_wiki=true` 的 gold 的 Recall；
- 对 `recommendable=true` 的 gold 的 Recall。

## 3. 教师问题一：如何建立材料研发通用多阶段流程

材料研发不能被强制表示为唯一线性过程。建议采用“宏观阶段 + 可选子阶段 + 输入输出”的层次化流程。

### 3.1 通用宏观阶段

| 编号 | 宏观阶段 |
|---|---|
| S1 | 需求与目标定义 |
| S2 | 已知数据获取与整理 |
| S3 | 候选材料生成 |
| S4 | 性质计算或性质预测 |
| S5 | 候选筛选与排序 |
| S6 | 稳定性与可合成性评估 |
| S7 | 实验设计与材料合成 |
| S8 | 表征与性质测量 |
| S9 | 模型或结论验证 |
| S10 | 反馈迭代与优化 |

每个宏观阶段下设置子阶段。例如：

```text
S2 数据获取与整理
├─ 数据库检索
├─ 数据清洗
├─ 实体对齐
├─ 特征构造
└─ 训练/验证/测试划分

S4 性质计算或预测
├─ DFT 计算
├─ 势函数模拟
├─ 机器学习训练
├─ 迁移学习
└─ 不确定性估计

S6 稳定性与可合成性评估
├─ 形成能评估
├─ 凸包稳定性
├─ 动力学稳定性
├─ 声子稳定性
└─ 可合成性预测
```

### 3.2 Task 应结构化表达

建议：

\[
Task=(Material,Goal,Property,Input,Output,Method,Stage,Role,Constraint)
\]

示例：

```json
{
  "material_scope": ["inorganic crystals"],
  "goal": "predict thermodynamic stability",
  "target_properties": ["formation energy", "energy above hull"],
  "input_entity": ["crystal structure", "composition"],
  "output_entity": ["stability score"],
  "method_family": ["machine learning"],
  "required_stages": ["data preparation", "model training", "validation"],
  "dataset_roles": ["training", "external validation"],
  "constraints": {
    "availability": "public",
    "data_origin": "DFT"
  }
}
```

### 3.3 阶段归属应建立在 DatasetUse 上

不能永久地把某个 Dataset 归入单一阶段。同一数据集在不同任务中可以有不同阶段和角色：

```text
DatasetUse(Materials Project, Task A)
→ stage = model training
→ role = training data

DatasetUse(Materials Project, Task B)
→ stage = candidate screening
→ role = candidate pool
```

因此，`DatasetUse` 是阶段匹配和使用角色匹配的主要语义单元。

## 4. 教师问题二点一：材料范围与任务范围的优先级

固定“材料优先”或固定“任务优先”都不理想，应根据查询特异性自适应选择。

### 4.1 为什么不能固定材料优先

“无机材料”“晶体材料”范围很宽，信息量低。如果材料范围优先，会召回大量通用晶体数据库，而忽视明确的形成能、带隙或可合成性任务。

### 4.2 为什么不能固定任务优先

“二维磁性材料的带隙预测”中的二维磁性材料非常具体。如果只强调带隙预测，可能召回大量三维无机材料数据。

### 4.3 自适应权重

可以定义：

\[
Specificity(x)=-\log\frac{freq(x)}{N}
\]

再计算：

\[
w_m=\frac{e^{s_m}}{e^{s_m}+e^{s_t}},\qquad w_t=1-w_m
\]

其中，`s_m` 为材料范围特异性，`s_t` 为任务和性质特异性。

### 4.4 最小可实施规则

```text
材料描述包含具体化学体系、维度、结构原型或元素限制
→ material-first

材料只是不具体的“无机材料/晶体材料”，但目标性质明确
→ task/property-first

材料与任务都具体
→ 两路并行召回，再加权融合
```

无论采用哪种策略，都应分别保留材料路线和任务路线的最低候选配额，防止某一路在融合前被完全截断。

## 5. 教师问题二点二：相似任务及其关联数据集如何排序

建议采用两级排序，而不是直接把所有页面映射为 Dataset 后统一排序。

### 5.1 第一级：相似 Task 排序

\[
S_{task}(q,t)=
w_mM_{material}
+w_gM_{goal}
+w_pM_{property}
+w_sM_{stage}
+w_iM_{input/output}
+w_cM_{constraint}
\]

初始权重可以设为：

| 维度 | 初始权重 |
|---|---:|
| material_match | 0.25 |
| goal_match | 0.20 |
| property_match | 0.25 |
| stage_match | 0.10 |
| input_output_match | 0.10 |
| constraint_match | 0.10 |

材料和任务权重随后由第 4 节的特异性策略调整。

### 5.2 第二级：Task 下的 DatasetUse/Dataset 排序

\[
S_{use}(q,t,u,d)=
0.30S_{task}
+0.20M_{property/use}
+0.15M_{stage}
+0.15M_{role}
+0.10M_{material}
+0.10A_{availability}
\]

再加入证据质量：

\[
S_{evidence}=
SourceQuality\times PathReliability\times UseCompleteness
\]

数据集总分可定义为：

\[
S(d)=
\max_{t,u}
\left(S_{use}(q,t,u,d)\times S_{evidence}\right)
+\lambda\log(1+n_{relevant\_uses})
\]

其中只统计与当前查询相关的 DatasetUse，数量加分需要对数缩放和封顶。

每个候选应保存：

```json
{
  "dataset_id": "D_materials_project",
  "best_task_id": "T_Pxxx_01",
  "best_use_id": "DU_Pxxx_001",
  "task_similarity": 0.82,
  "use_compatibility": 0.76,
  "constraint_compliance": 1.0,
  "evidence_quality": 0.90,
  "final_score": 0.79
}
```

## 6. 教师问题三：task-specific 数据集如何检索

首先区分三类数据集。

### 6.1 公共原始数据集

例如 Materials Project、OQMD、JARVIS-DFT 和 ICSD，可被多个任务复用。

### 6.2 公共任务数据集或 Benchmark

例如 Matbench、QM9、FreeSolv 和 ESOL，具有明确任务边界，但公开且可复用。

### 6.3 论文专属派生数据集

例如：

```text
Materials Project
+ 元素筛选
+ 数据清洗
+ 标签构造
+ 数据划分
→ author-curated task-specific dataset
```

这类数据集不能无条件当作可下载的公共数据集，也不能简单丢弃。

### 6.4 双层推荐

建议输出：

1. 可直接使用的数据集；
2. 可从公共源复现的 task-specific 数据集构建方案。

如果没有直接可获取的完全匹配数据集，可以输出：

> 建议以 Materials Project 为公共源，按相关论文记录的元素范围、目标字段、去重规则和划分方式构建任务数据集。

### 6.5 两条检索路线

```text
直接查找：
Query → Task/Property/Material → task-specific DatasetUse → Dataset

构建查找：
Query → 相似 Task → DatasetUse → source Dataset
                         ↓
             filter/construction/split recipe
```

建议在检索索引内部增加：

```text
dataset_type:
- general_public
- task_benchmark
- author_curated_public
- author_curated_unavailable
- derived_subset
```

task-specific 匹配可采用：

\[
S_{taskSpecific}=
M_{material}\times
M_{property}\times
M_{task}\times
M_{stage}\times
Reusability
\]

乘法可以防止一个候选仅靠单个维度的高分掩盖关键维度冲突。

## 7. 诊断基线：每个指标代表什么

### 7.1 首先明确评测单位

虽然 Dense、BM25 和 RRF 返回的是页面，但 gold 是数据集。因此每个阶段都必须将页面转换成“该阶段已经能够支持的数据集集合”，然后与 gold 数据集比较。

对于页面 `p`，定义生产流程允许的映射 `map(p)`：

- Dataset 页面映射到该 Dataset；
- DatasetUse 页面映射到其使用的 Dataset；
- Stage 页面映射到该阶段直接连接的 DatasetUse 所使用的数据集；
- Task 页面映射到该任务直接连接的 DatasetUse 所使用的数据集；
- 派生数据集按当前系统规则映射到公共源时，必须同时记录“精确派生实体”和“公共源实体”。

不能为了提高指标使用生产流程中不存在的无限图路径。诊断映射必须和真实检索阶段的操作一致。

对于问题 \(q\)，gold 集合为 \(G_q\)，阶段候选集合为 \(C_q^{stage}\)：

\[
Recall_q^{stage}=
\frac{|G_q\cap C_q^{stage}|}{|G_q|}
\]

数据集名称应分别按照 Strict、Canonical 和 Family 三种规则计算。诊断时至少以 Canonical 为主，同时报告 Family。

### 7.2 Dense Recall@K

**定义：** 对每条 Dense 查询取 Top-K 页面，合并全部 Dense 查询结果；按该阶段允许的页面映射得到数据集集合，再计算 gold Recall。

\[
DenseRecall@K=
\frac{|G_q\cap map(\cup_i Dense_i@K)|}{|G_q|}
\]

**含义：**

- 衡量向量检索是否提供了足够的语义召回能力；
- 如果很低，问题主要在页面文本、Embedding、查询改写、索引粒度或 Top-K；
- 它是 Dense 通道在后续融合前的理论上限之一。

建议同时计算：

- `Dense direct Recall@K`：只允许 Dataset 和 DatasetUse 直接映射；
- `Dense mappable Recall@K`：允许 Task/Stage 按生产规则映射。

二者差距大，说明 Dense 更容易召回任务语义页面，而不是数据集或用途证据页面。

### 7.3 BM25 Recall@K

**定义：** 对全部 BM25 查询的 Top-K 页面取并集并映射为数据集，再计算 Recall。

\[
BM25Recall@K=
\frac{|G_q\cap map(\cup_i BM25_i@K)|}{|G_q|}
\]

**含义：**

- 衡量数据集名称、缩写、性质字段和材料术语等精确词项的覆盖能力；
- 如果 BM25 明显低于 Dense，可能是查询缺少别名、字段词或页面分词不足；
- 如果 BM25 能命中而 RRF 丢失，问题在融合权重或截断，而不在 BM25 本身。

### 7.4 Hybrid Union Recall@K

建议额外记录 Dense 与 BM25 并集的 Recall：

\[
UnionRecall@K=
\frac{|G_q\cap(C_q^{dense}\cup C_q^{bm25})|}{|G_q|}
\]

**含义：**

- 表示两条基础通道共同能够达到的候选覆盖上限；
- `Union Recall - max(Dense Recall, BM25 Recall)` 反映两路检索的互补收益；
- 如果互补收益接近 0，说明查询或索引过于同质化。

### 7.5 RRF Recall@40

**定义：** 对 RRF 融合后实际保留的 Top-40 种子页面进行映射，计算 gold Recall。

\[
RRFRecall@40=
\frac{|G_q\cap map(RRF@40)|}{|G_q|}
\]

**含义：**

- 衡量多路融合和页面级 Top-K 截断是否保留了正确候选；
- 若 Union Recall 高而 RRF Recall 低，说明正确页面虽然被某条查询召回，但被等权 RRF 或 Top-40 截断压掉；
- 可用于判断是否需要通道权重、查询质量权重、去重或每路候选保底配额。

### 7.6 Graph/Candidate Recall

**定义：** RRF Top-40 经图扩展和 `aggregate_dataset_candidates()` 后，全部 DatasetCandidate 对 gold 的 Recall。

\[
CandidateRecall=
\frac{|G_q\cap C_q^{candidate}|}{|G_q|}
\]

**含义：**

- 衡量页面到 Dataset 的映射和图扩展能否补回正确候选；
- 是当前候选生成阶段对最终 Recall 的直接上限；
- 如果 RRF Recall 低而 Candidate Recall 上升，说明图扩展提供了正向增益；
- 如果 Candidate Recall 不升但候选数量暴增，说明图扩展主要增加噪声；
- 如果 RRF 中已有相关页面，但 Candidate Recall 仍低，可能是边缺失、DatasetUse 连接错误、派生数据集映射错误或 recommendable 过滤造成。

建议同时记录：

\[
GraphGain=CandidateRecall-RRFRecall
\]

以及：

\[
ExpansionNoise=
\frac{\text{扩展后候选数}-\text{扩展前候选数}}
{\max(1,\text{扩展前候选数})}
\]

GraphGain 很小而 ExpansionNoise 很高，说明图扩展需要收紧。

### 7.7 Deterministic Recall@30

**定义：** 全部 DatasetCandidate 经过确定性重排后，只取前 30 名计算 Recall。

\[
DetRecall@30=
\frac{|G_q\cap DeterministicRank@30|}{|G_q|}
\]

**含义：**

- 判断确定性特征和权重是否将正确候选保留给 LLM rerank；
- 如果 Candidate Recall 高而 DetRecall@30 明显下降，说明任务、材料、性质、阶段、角色、可用性或流行度分数存在排序偏差；
- 当前系统只有前 30 个候选会进入 LLM rerank，因此它也是 LLM 能够修正排序的上限。

建议同时报告 `DetRecall@5/@10/@20/@30`，观察 gold 是稳定在前部还是只在扩大 K 后才出现。

### 7.8 LLM Rerank Recall@K

虽然最初基线列表没有单独列出，但建议加入。

**定义：** LLM 重排后的候选前 K 对 gold 的 Recall。

**含义：**

- 比较 `LLM Recall@K` 与 `Det Recall@K`，可以判断 LLM 是提升还是破坏了排序；
- 若前 30 的候选不变，只是顺序变化，则 `LLM Recall@30` 应与 `Det Recall@30` 相同；
- 重点应比较 @1、@3、@5 和 gold 的平均排名变化。

### 7.9 Final Recall@K

**定义：** recommend 或 minimum 集合选择后最终返回的前 K 个数据集对 gold 的 Recall。

\[
FinalRecall@K=
\frac{|G_q\cap Final@K|}{|G_q|}
\]

**含义：**

- 衡量最终选择策略保留真实数据集的能力；
- 如果 LLM Rerank Recall@5 高，但 Final Recall@5 低，说明家族去重、最小集合、覆盖规则、数量限制或约束逻辑删除了正确结果；
- 最终 Precision、Recall 和 F1 是面向用户的总体效果，但不能单独定位故障来源。

### 7.10 Wiki-covered Recall

定义可由当前 Wiki 表达且允许推荐的 gold 集合：

\[
G_q^{covered}=
\{g\in G_q\mid exists\_in\_wiki(g)=true\}
\]

然后：

\[
CoveredRecall=
\frac{|G_q^{covered}\cap C_q|}{|G_q^{covered}|}
\]

**含义：**

- 将知识库覆盖问题与检索算法问题分离；
- `Overall Recall` 低但 `Covered Recall` 高，说明主要瓶颈是 Wiki 覆盖；
- 两者都低，才说明检索或排序本身存在较大问题。

### 7.11 MRR 和首个命中排名

对于每个问题，记录排名最高的 gold 的位置 `rank_first_gold`：

\[
MRR=\frac{1}{|Q|}\sum_q\frac{1}{rank_q}
\]

若没有命中，该问题贡献 0。

**含义：**

- Recall 只判断是否出现，MRR 判断第一个正确结果是否足够靠前；
- 特别适合评价用户通常只看第一个推荐结果的场景。

### 7.12 NDCG@K

如果有多个 gold，且能为不同 gold 设置相关性等级，可使用 NDCG。

例如：

- 论文直接使用的精确数据集：3 分；
- 同一 canonical 实体：2 分；
- 同一家族且可替代：1 分；
- 无关：0 分。

**含义：**

- 同时考虑排序位置和不同相关等级；
- 比将所有 gold 当作完全等价更适合公共源、派生集和家族数据集并存的情况。

## 8. 如何实际建立诊断基线

### 8.1 第一步：冻结测试集

不要直接以自由格式 DOCX 作为程序内部基线。可以继续用 DOCX 录入，但应先转换并人工校验为固定 JSONL。

建议每行一个测试问题：

```json
{
  "case_id": "Q001",
  "question": "用户问题全文",
  "gold_datasets": [
    {
      "raw_name": "Materials Project (MP) database",
      "canonical_id": "materials_project",
      "family_id": "materials_project_family",
      "exists_in_wiki": true,
      "recommendable": true,
      "dataset_id": "D_materials_project"
    }
  ],
  "notes": "论文实际使用；人工核验完成"
}
```

必须人工检查：

- 数据集拆分是否正确；
- 别名是否正确；
- 派生集与公共源是否被错误合并；
- gold 是否真实存在于 Wiki；
- 不可公开的作者专属数据集是否被标注。

### 8.2 第二步：为检索程序增加阶段快照

每次运行至少保存：

```json
{
  "case_id": "Q001",
  "query_plan": {},
  "dense_rankings": [],
  "bm25_rankings": [],
  "rrf_ranking": [],
  "rrf_seed_top40": [],
  "expanded_pages": [],
  "dataset_candidates": [],
  "deterministic_ranking": [],
  "llm_ranking": [],
  "final_selection": []
}
```

每个 DatasetCandidate 应记录：

```json
{
  "dataset_id": "D_materials_project",
  "source_pages": ["T_Pxxx_01", "DU_Pxxx_001"],
  "supporting_use_ids": ["DU_Pxxx_001"],
  "graph_paths": [],
  "retrieval_score": 0.08,
  "graph_score": 0.72,
  "task_match": 0.80,
  "material_match": 0.60,
  "property_match": 1.00,
  "stage_match": 0.50,
  "role_match": 1.00,
  "deterministic_score": 0.75,
  "llm_score": 0.83,
  "final_score": 0.77
}
```

当前运行轨迹已经保存了部分内容，但仍需确认以下信息可以被稳定、结构化读取：

- RRF Top-40 种子与完整 RRF 列表是否分开保存；
- 扩展页面及每条路径是否完整保存；
- 聚合前页面如何映射为 Dataset；
- 每个候选在每一阶段的排名；
- gold 被删除时的具体原因；
- JSON 输出必须是严格合法、统一 UTF-8 编码的 JSON。

### 8.3 第三步：建立统一的页面到数据集映射

评估程序不能自行发明比生产检索更宽松的映射。建议直接复用检索程序中的 WikiStore、边关系和聚合规则。

为每个页面输出：

```json
{
  "doc_id": "T_P005_01",
  "direct_dataset_ids": [],
  "production_mapped_dataset_ids": [
    "D_materials_project",
    "D_oqmd",
    "D_jarvis_dft"
  ]
}
```

同时区分：

- 直接 Dataset/DatasetUse 命中；
- 由 Task/Stage 映射得到；
- 由图扩展得到；
- 由派生集映射到公共源得到。

### 8.4 第四步：逐阶段计算指标

建议每个问题输出一行：

| case_id | gold_count | dense_r@30 | bm25_r@30 | union_r@30 | rrf_r@40 | candidate_r | det_r@30 | llm_r@5 | final_r@5 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Q001 | 4 | 0.75 | 0.50 | 1.00 | 0.75 | 1.00 | 0.75 | 0.50 | 0.50 |

然后聚合：

- Macro：先计算每个问题，再取平均；
- Micro：汇总所有 TP、FP 和 FN 后计算；
- 分别输出 Strict、Canonical 和 Family；
- 同时输出 Wiki-covered 版本。

### 8.5 第五步：自动定位 gold 消失阶段

每个 gold 都应记录生存状态：

| gold | Dense | BM25 | RRF | Candidate | Det-30 | LLM-5 | Final |
|---|---|---|---|---|---|---|---|
| OQMD | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| JARVIS | ✓ | ✗ | ✓ | ✓ | ✓ | ✗ | ✗ |
| Experimental formation energy | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |

并自动生成失败原因，例如：

```text
Experimental formation energy dataset
首次消失阶段：RRF Top-40
此前状态：BM25 查询第 27 名命中
可能原因：等权 RRF 下仅被一条查询命中，被多次命中的通用页面压低
```

这比只看最终推荐结果更能指导代码修改。

### 8.6 第六步：固定运行条件

建立基线时应冻结：

- Wiki 版本及哈希；
- 索引版本；
- Embedding 模型和维度；
- Dense/BM25 Top-K；
- RRF 参数；
- 图扩展深度和边权重；
- candidate_top_k；
- LLM 模型、提示词、温度和重试策略；
- recommend/minimum 模式；
- 数据集名称规范化规则。

每次实验只改变一个主要因素，并记录实验编号。

### 8.7 第七步：进行消融实验

建议实验顺序：

| 实验 | 改动 |
|---|---|
| B0 | 当前完整系统 |
| B1 | 关闭图扩展 |
| B2 | 只允许强语义图路径 |
| B3 | 全历史 DatasetUse 改为 supporting + relevant Top-3 |
| B4 | 增加相似 Task 一级排序 |
| B5 | 固定材料优先 |
| B6 | 固定任务优先 |
| B7 | 自适应材料/任务权重 |
| B8 | 关闭 LLM rerank |
| B9 | 加入约束合规复核 |

每次比较：

- Candidate Recall 是否提升；
- Det Recall@30 是否提升；
- Final Precision/Recall/F1 是否提升；
- MRR 是否提升；
- 平均候选数和运行时间是否增加；
- 改进是否只来自 Family 宽松匹配。

## 9. 如何根据诊断结果决定修改位置

| 观察结果 | 主要问题 | 优先修改 |
|---|---|---|
| Dense Recall 低，BM25 高 | 语义查询或页面向量表达不足 | Query rewrite、页面文本、Embedding |
| BM25 Recall 低，Dense 高 | 术语、别名和字段词不足 | 受控词表、BM25 查询、分词 |
| Union Recall 高，RRF Recall 低 | 融合或 Top-40 截断 | 通道权重、查询去重、保底配额 |
| RRF Recall 低，Candidate Recall 上升 | 图扩展有效 | 保留但控制噪声 |
| Candidate Recall 不升、候选暴增 | 图扩展噪声大 | 路径类型、边权、传播约束 |
| Candidate Recall 高，Det Recall@30 低 | 确定性特征或历史用途偏置 | relevant DatasetUse、动态权重 |
| Det Recall@5 高，LLM Recall@5 低 | LLM 重排破坏排序 | 证据选择、提示词、跨批校准 |
| LLM Recall@5 高，Final Recall@5 低 | 集合选择删除 gold | family 去重、minimum、覆盖逻辑 |
| Overall Recall 低，Covered Recall 高 | Wiki 覆盖不足 | 扩充 Wiki，而非修改排序 |
| Family 高、Canonical 低 | 精确实体/版本识别不足 | 数据集本体、来源和派生关系 |

## 10. 推荐的新完整检索流程

```text
用户问题
  ↓
结构化 QueryPlan
  ├─材料范围
  ├─任务目标
  ├─目标性质
  ├─输入/输出
  ├─研发阶段
  ├─数据角色
  └─硬/软约束
  ↓
判断材料与任务的特异性
  ↓
多路分层召回
  ├─材料路线
  ├─任务/性质路线
  ├─阶段/角色路线
  ├─约束路线
  └─联合语义路线
  ↓
带权融合与每路候选保底
  ↓
相似 Task 一级排序
  ↓
受路径语义约束的图扩展
  ↓
提取 supporting DatasetUse 和 relevant DatasetUse
  ↓
Dataset 二级排序
  ├─任务适配
  ├─材料适配
  ├─性质适配
  ├─阶段/角色适配
  ├─约束合规
  └─证据质量
  ↓
公共数据集与 task-specific 数据集分流
  ↓
约束合规性复核
  ↓
Top-K 推荐或最小覆盖集合
  ↓
证据链与 task-specific 构建方案
```

## 11. 推荐的实施顺序

1. 建立逐阶段诊断基线，不立即修改大规模评分逻辑；
2. 人工校验 13 组 gold 和 Wiki 覆盖状态；
3. 计算 Dense、BM25、RRF、Candidate、Deterministic、LLM 和 Final 的逐层 Recall；
4. 找出每个 gold 首次消失的阶段；
5. 优先将全历史 DatasetUse 改为 `supporting_use_ids + relevant Top-3`；
6. 加入相似 Task 一级排序；
7. 比较材料优先、任务优先和自适应权重；
8. 增加 task-specific 数据集双层推荐；
9. 加入最终约束合规复核；
10. Candidate Recall 足够高之后，再优化 minimum 集合。

## 12. 可以形成的论文核心贡献

系统的核心贡献不宜只描述为 Dense、BM25、RRF、图扩展和 LLM rerank 的组合。更有材料领域意义的表述是：

> 面向材料研发任务，提出一种基于材料—任务分层匹配、研发阶段建模和查询相关 DatasetUse 证据路径的数据集推荐方法，同时支持公共数据集推荐与 task-specific 数据集复现。

其中最需要通过实验验证的研究假设是：

1. 材料与任务的自适应分层匹配优于固定等权匹配；
2. 查询相关 DatasetUse 优于全部历史 DatasetUse；
3. 受语义约束的图扩展优于无差别两跳扩展；
4. 两级 Task–Dataset 排序优于直接 Dataset 聚合排序；
5. 公共数据集与 task-specific 构建方案分流能够提高结果可用性和解释性。
